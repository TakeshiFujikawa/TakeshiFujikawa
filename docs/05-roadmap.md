# 5. 技術スタック案・開発ロードマップ

## 5-1. 技術スタック案

複数アプリ（GPS連携・ウェアラブル連携・カメラ・画像解析）を統合するため、
最終的にはモバイルアプリでの提供が前提になる。ただし設計検証・社内レビュー段階では
コストの低い構成から始め、段階的に本実装へ移行することを推奨する。

| フェーズ | 構成案 | 目的 |
|---|---|---|
| Phase 0：検証 | 本ドキュメント＋HTMLモックアップ（`mockups/`） | 画面構成・情報設計のレビュー、関係者との認識合わせ |
| Phase 1：プロトタイプ | React Native（Expo）＋ サーバーレスAPI（食事写真の解析・提案ロジック） | 実機での操作感（カメラ、GPS）の検証。最小機能（食事記録＋提案、ラン記録）から |
| Phase 2：本実装 | React Native（または Flutter）＋ バックエンドAPI＋ DB（PostgreSQL等）＋ 画像解析（マルチモーダルAIモデル連携） | 連携デバイス（体組成計・ウェアラブル）対応、コンディションスコア算出ロジックの実装 |

**画像解析（食事写真→品目・カロリー推定）について**：
マルチモーダル対応のLLM/画像認識APIを用いて「料理名・食材・推定量」を抽出し、
別途、栄養価データベース（食品成分データベース等）と突き合わせてカロリー・PFCを
算出する2段構成を推奨する（解析と栄養計算の責務を分離し、精度改善をしやすくするため）。

## 5-2. 開発ロードマップ（MVP優先）

### MVP（最小構成）— 「続けられる」ことを最優先に検証する

1. ホーム画面：コンディションスコア（簡易版：手動入力ベースでも可）
2. 食事記録：写真撮影 → 品目・カロリー推定 → 次の食事提案（条件1・3を中心に実装）
3. ラン記録：GPSでのスタート/ストップ、距離・ペースの記録

→ この3つだけで「記録の手間を減らし、次のアクションを示す」という
コアバリューを検証できる。

### 拡張フェーズ1

- ウェアラブル／スマート体組成計連携（自動記録化）
- コンディションスコアのフル算出ロジック（回復・活動・栄養の統合）
- 献立提案条件の拡張（条件2・4・5・6：コンディション連動、栄養バランス、多様性）

### 拡張フェーズ2

- トレンド／週次レポートの自動生成
- 提案ロジックのパーソナライズ（ユーザーのフィードバック・修正履歴からの学習）
- 実績・継続のモチベーション設計（過度なゲーミフィケーションは複雑化を招くため慎重に検討）

## 5-3. 検証すべき主要リスク

- **画像認識の精度**：和食・外食メニュー・盛り付けの個人差にどこまで対応できるか
  → MVPでは「ユーザーが確認・修正できるUI」を必須とし、精度への過度な依存を避ける
- **デバイス連携の対応範囲**：WHOOP・ヘルスプラネット（オムロン）・各種ウェアラブルとの
  API/Bluetooth連携可否を早期に調査する
- **「続けられるか」**：記録の手間を本当に減らせているか、実際のユーザーで検証する
  （これが本アプリの存在意義そのものであるため、最優先で検証する）
