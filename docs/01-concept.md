# 1. コンセプト

## 1-1. 課題認識：なぜ3アプリを融合するのか

| アプリ | 強み | 一方で… |
|---|---|---|
| **WHOOP** | HRV・睡眠・回復(リカバリー)・ストレイン(運動負荷)を毎日スコア化し「今日どれだけ動けるか」を示す | 専用バンドが必要。指標が専門的でスコアの意味を理解しにくい |
| **ヘルスプラネット** | 体重・体組成・血圧・食事記録を蓄積しグラフ化できる | 入力項目が多く、習慣化のハードルが高い。提案力が弱い（記録止まり） |
| **ASICS Runkeeper** | GPSでのラン/ウォーク記録、ペース・ルート・実績管理 | 運動記録に特化しており、回復や食事と紐付かない |

→ ユーザーは「回復（睡眠・コンディション）」「運動」「食事・体組成」を
**別々のアプリで別々に確認し、自分の頭の中で統合**しなければならない。
この“統合の手間”こそが最大のペインであり、削るべき複雑さ。

## 1-2. コンセプト：3つを1つの数字に集約する

> **「今日のコンディションスコア」ひとつだけ見れば、何をすべきかがわかる**

WHOOPの「リカバリー」、ヘルスプラネットの「体組成トレンド」、Runkeeperの「運動負荷」を
裏側で統合し、ユーザーには **0〜100の単一スコアと、それに基づく今日のアクション提案**
だけをまず見せる。詳細データは「もっと見る」で深掘りできる二段構成にする。

## 1-2-1. 一番大事な体験：「撮ったら、ぜんぶ出てくる」

> **写真を撮るだけで、カロリーもPFCも体組成との照合もすべて自動で反映され、
> そのまま次の食事の提案まで出てくる。**

これが本アプリの最も中心的なユーザー体験であり、「シンプルでわかりやすい」を
体現する場面そのもの。ユーザーがやることは「撮る」だけで、

- 料理名・推定カロリー・PFC（タンパク質/脂質/炭水化物）が自動で数値化され、
- その日の摂取バランス・残りカロリー枠に即座に反映され、
- 体組成データ（[3章 課題の整理](03-meal-suggestion-spec.md)）や当日のコンディションと
  突き合わされ、
- **「次は何を食べるとよいか」が5案、理由付きでその場に表示される**

…という一連の処理が、ユーザーの目の前で「数字が次々と埋まっていく」体験として
完結する（[2-4 食事画面](02-screens-and-features.md)、
[mockups/meal.html](../mockups/meal.html)を参照）。

入力の手間（数値の手入力・条件の手動チェック）を一切ユーザーに負わせず、
「撮る」という1アクションだけで「記録・分析・提案」のすべてが完了する ―
これこそが3アプリの良さを併せ持ちながら、それぞれより簡単にする本アプリの中核。

```
┌─────────────────────────────┐
│   今日のコンディション          │
│        78 / 100  「good」    │
│                              │
│  💤 回復   🏃 活動   🍽 栄養   │
│   82       70       80       │
│                              │
│  → 今日のおすすめ：           │
│    軽めのジョグ + 高たんぱく食  │
└─────────────────────────────┘
```

## 1-3. デザイン原則（簡略化の指針）

1. **数字をひとつに集約する** — リカバリー・ストレイン・体組成・運動量という
   4種類の異なる指標を、ユーザーには「コンディションスコア」という1つの言葉に翻訳する。
   詳細を知りたい人だけが内訳を見られるようにする。
2. **記録は自動化・最小化する** — 体重や運動はウェアラブル/スマート体組成計と連携して自動取得。
   ユーザーが手で入力するのは「食事の写真を撮る」程度に留める。
3. **「次に何をするか」を必ず添える** — スコアやグラフを見せるだけで終わらせず、
   常に「だから今日はこうしよう」という1アクションを提示する（後述の献立提案もこの一部）。
4. **専門用語を翻訳する** — HRV・ストレイン・TSSのような専門指標は、
   「今日は無理せず」「今日はもうひと押しできる」のような生活言語に変換して提示する。
5. **画面数を絞る** — タブは「ホーム / 記録 / 走る / 食事 / トレンド」の5つのみ。
   設定や詳細データはホームから1階層深いところに格納する。

## 1-4. ターゲットユーザー

- 健康診断や体型の変化が気になり始めた30〜50代
- フィットネスアプリを複数試したが、続かなかった／情報過多で挫折した人
- 「頑張って記録する」のではなく「自然に続けられる」管理を求めている人

ヘビーユーザー向けの高機能アプリ（WHOOP等）から一段下の、
**「迷わず続けられるシンプルさ」を求める層**を狙う。

## 1-5. 本設計の前提となる利用シナリオ

本アプリは、以下の「健康管理プログラム」での実利用を主軸に設計する
（チャットタイトル：**「2026年5月30日からの健康管理プログラム」**）。

| 項目 | 内容 |
|---|---|
| プログラム開始日 | 2026年5月30日 |
| 期間 | 1年間（2027年5月末ごろまで） |
| 目標 | **1年かけて体重を15kg減らしながら、同時に筋力をつけ、健康な身体づくりを行う** |

この目標は「減量」と「筋力アップ」を**同時に**狙う、いわゆる
**ボディリコンポジション（体組成の作り直し）型**の目標であり、
単純なカロリー制限だけでは成立しない（筋肉量の減少を招きやすいため）。
そのため本アプリでは、以下を特に重視した設計とする。

- **回復（睡眠・コンディション）と運動負荷のバランス管理**
  　筋力トレーニングの効果を引き出すには、適切な回復が不可欠。
  　WHOOP由来の「コンディションスコア」がこの目標達成の鍵となる。
- **極端な減量ではなく、緩やかなカロリー収支管理**
  　1年で15kgという長期目標は、急激な制限よりも持続可能なペースでの
  　管理に向いている。ヘルスプラネット由来の体組成記録で進捗を可視化する。
- **筋力アップを支える栄養（特にたんぱく質）の確保**
  　献立提案機能（[3章](03-meal-suggestion-spec.md)）で、減量と筋力アップを
  　両立する栄養バランスを重点的に提案する。
- **運動と栄養の連動**
  　Runkeeper由来の運動記録（消費カロリー・運動強度）を、その日の
  　献立提案に反映し、「動いた分、何をどう補うか」を自動で示す。

ホーム画面の「目標」（[2-2記録](02-screens-and-features.md)）には、
このプログラムの目標（1年で-15kg・筋力アップ）を初期設定として表示する。
